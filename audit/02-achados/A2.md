# ALTO

### A2-001: Deadlock permanente no OAuth do Google — `shutdown()` num socket de escuta não desperta `accept()` no macOS
- Severidade: **ALTO** (fronteira com CRÍTICO: deixa `xcodebuild test` sem nunca terminar e trava o fluxo Conectar até reiniciar o app — ver justificativa)
- Confiança: **CONFIRMADO**
- Local:
  - `Papagaio/Integracao/SessaoOAuthGoogle.swift:440` (cancelamento), `:447` (`parar()`), `:491-495` (`accept` bloqueante), `:160-185` (task group), `:353-357` (fila de socket)
  - `PapagaioTests/OAuthGoogleTests.swift:47-65` e `:67-83` (os dois testes que travam)
  - Sintoma executado por terceiro nesta auditoria: `audit/00-mapa.md:384-402`
- Evidência: duas rotas de cancelamento desbloqueiam o `accept` com `shutdown` no **socket de escuta**:
  ```swift
  // SessaoOAuthGoogle.swift:438-441
  } onCancel: {
      conexao.cancelar()
      Darwin.shutdown(listener.fileDescriptor, SHUT_RDWR)   // listener = socket de ESCUTA
  }
  // SessaoOAuthGoogle.swift:444-447
  func parar() {
      conexao.cancelar()
      if let descritor = listener?.fileDescriptor, descritor >= 0 {
          Darwin.shutdown(descritor, SHUT_RDWR)             // idem
      }
  ```
  E o worker fica bloqueado em `Darwin.accept(socket, …)` (`:491-495`), de onde só sai
  com um cliente novo ou com erro — `shutdown` em fd de escuta não o interrompe.
  **Medi aqui, nesta execução**, com um programa Swift mínimo (`/tmp/a2_shutdown_accept.swift`,
  compilado com `swiftc`, executado no mesmo macOS desta máquina):
  ```
  shutdown(listenFD) retornou -1, errno=57 (Socket is not connected)
  RESULTADO: accept() NÃO despertou em 2 s após shutdown() -> bloqueado para sempre
  ```
  Ou seja: `shutdown()` em socket de escuta **nem sequer retorna sucesso** no XNU (ENOTCONN/57),
  logo o `accept()` nunca é acordado, a continuação de `withCheckedThrowingContinuation`
  (`:424-437`) nunca retoma e o task group de `aguardarCodigo(no:tempoLimite:)` (`:164-184`)
  nunca termina (o grupo espera todos os filhos antes de sair).
  A baseline desta auditoria registrou exatamente esse sintoma: os testes
  `OAuthGoogleTests.swift:47` e `:67` iniciaram e **nunca terminaram**;
  `xcodebuild test` não emitiu linha final e foi encerrado com SIGTERM/`TEST_EXIT=143`
  (`audit/00-mapa.md:384-402`).
- Cenário de falha:
  1. **App:** pessoa clica em Conectar Google Calendar → navegador abre → ela **não conclui** (fecha a aba, o redirect nunca chega). Em 180 s (`:144`) o timeout dispara → `group.cancelAll()` + `await servidor.parar()` → `shutdown` falha em silêncio → o grupo espera o filho em `accept` **para sempre** → `fluxoDeAutorizacao()` nunca retorna → `GoogleCalendarViewModel.conectar` fica preso em `await tarefa.value` (`GoogleCalendarViewModel.swift:69`) → `tarefaDeConexao` nunca vira `nil` → o `guard tarefaDeConexao == nil` (`:61`) silencia **todas** as tentativas seguintes. Recuperação: reiniciar o app.
  2. **Testes/CI:** os 2 testes de timeout/cancelamento penduram para sempre → o run de testes do alvo nunca completa (é o que a baseline já observou; o badge do repo está "CI - failing").
  3. A cada tentativa travada o fd de escuta e o worker da fila `papagaio.oauth.google.loopback` ficam retidos até o processo morrer.
- Como reproduzir: `./Scripts/… ` → `PAPAGAIO_TEST_MODE=1 xcodebuild test -project Loro.xcodeproj -scheme Loro -destination 'platform=macOS' …` e observar que `OAuthGoogleTests` "Cancelar a espera…" e "Timeout do OAuth…" nunca emitem resultado (baseline: `audit/00-mapa.md:373-418`). Para o mecanismo puro: `swiftc /tmp/a2_shutdown_accept.swift && ./a2_shutdown_accept` (já feito, saída acima). Instruments/`sample` do processo pendurado mostra o worker ocioso *fora* de `accept` só porque o `sample` foi tirado quando o processo-teste já tinha o fd em outro estado; a prova decisiva é o experimento acima.
- O que procurei para refutar: (a) verifiquei se algum caminho chama `close()` no fd de escuta — não chama, e o comentário em `:449-451` explica que fechar foi evitado de propósito; (b) verifiquei se `conexao.cancelar()` (`:595-600`) desbloquearia — ela só faz `shutdown` no **cliente** aceito, que não existe nesse cenário; (c) verifiquei se `Darwin.shutdown` era chamado no fd do cliente em `onCancel` — não, é o `listener` local (desembrulhado pelo `guard let listener` de `:417`); (d) verifiquei se o grupo teria algum `timeout` interno — não tem, só o `Task.sleep` de 180 s/50 s que depende do grupo terminar; (e) verifiquei o teste `cancelarOAuthComClienteSilencioso` (`OAuthGoogleTests.swift:169-194`), que **passa** justamente porque ali já existe um cliente conectado e o `accept` retorna — consistente com "só penduram os dois testes sem conexão".
- Causa raiz: uso de `shutdown()` como mecanismo de interrupção de `accept()` — presunção POSIX que o XNU não implementa para sockets de escuta (retorna `ENOTCONN`).
- Correção sugerida (mínima, baixo risco): acordar o `accept` com uma **conexão de si mesmo** — guardar a porta devolvida por `getsockname` (`:404`) e, em `parar()`/`onCancel`, fazer um `connect()` não bloqueante em `127.0.0.1:porta` após marcar `conexao.cancelar()`; o worker aceita, vê `conexao.cancelada == true` e lança `CancellationError` (já existe esse ramo em `:499-502`). Alternativa mais estruturada: substituir o `accept` bloqueante por `DispatchSource` de leitura no fd de escuta (cancelável). Não mexe no contrato público da classe.

### A2-002: Ditado de nota não tem caminho de cancelamento — microfone e `SFSpeechRecognitionTask` continuam ativos ao trocar de seção/sair da tela
- Severidade: **ALTO**
- Confiança: **PROVÁVEL**
- Local: `Papagaio/Funcionalidades/Detalhe/ArquivoDetalheView.swift:82`, `:513-520`, `:1386-1401`; `Papagaio/ViewModels/GravadorViewModel.swift:571-579`, `:415-469`
- Evidência:
  ```swift
  // ArquivoDetalheView.swift:82
  @State private var ditado = DitadoDeNota()
  // ArquivoDetalheView.swift:513-520  (.onDisappear)
  tarefaDeSalvamentoDasNotas?.cancel()
  salvarNotasAgora()
  reprodutor?.encerrar()      // o player é encerrado…
  reprodutor = nil            // …o ditado, não
  ```
  `DitadoDeNota.cancelar()` (`GravadorViewModel.swift:571-579`) existe mas **não tem nenhum
  chamador**: `grep -rn "\.cancelar()"` em `Papagaio/`, `PapagaioCore/Sources/` e
  `PapagaioTests/` devolve 8 ocorrências, todas de `gravador.cancelar()` (PapagaioApp,
  ContentView, PainelFlutuanteDeGravacao), `conexao.cancelar()` (OAuth) e
  `sessao.cancelar()` (WhisperEngine) — nenhuma chamando `ditado.cancelar()`.
  Enquanto isso `DitadoDeNota.iniciar()` liga de fato a captura:
  ```swift
  // GravadorViewModel.swift:453-456 (CapturaDeDitado.iniciar)
  entrada.installTap(onBus: 0, bufferSize: 2_048, format: formato) { buffer, _ in
      pedidoDoTap.append(buffer)
      try? arquivo.write(from: buffer)
  }
  motor.prepare(); try motor.start()
  ```
- Cenário de falha:
  1. pessoa abre uma conversa → Notas → "Ditar" → estado `.gravando` com `AVAudioEngine` rodando;
  2. ela troca para a aba **Resumo/Transcrição** (o `secaoSelecionada` muda; `ArquivoDetalheView`
     continua viva, portanto o `@State ditado` — e com ele o `CapturaDeDitado` — continua retido):
     **o microfone segue capturando e o `SFSpeechRecognitionTask` segue mandando parciais**,
     atualizando `textoParcial` de um estado que ninguém desenha. O único sinal visível
     ("Ouvindo…", `NotasDaConversa.swift:239-248`) mora dentro da seção Notas, que não está na tela;
  3. o mesmo vale ao voltar (`onDisappear` não cancela): se o `@State` sobreviver à navegação
     (ex.: sheet por cima), a captura continua; se o `@State` for destruído, a parada passa a
     depender do `deinit` do `AVAudioEngine` — `CapturaDeDitado` **não tem `deinit`** (`:415-482`),
     ou seja, não há garantia explícita de `removeTap`/`motor.stop()` nesse caminho;
  4. além da privacidade, o `.caf` temporário `ditado-<uuid>.caf` (`:532-533`) só é apagado em
     `concluir`/`cancelar` — com a view destruída no meio, o arquivo fica em `temporaryDirectory`.
- Como reproduzir: abrir conversa → Notas → Ditar → falar → clicar em "Transcrição" e observar
  que o indicador de microfone do macOS permanece aceso (Preferences → Privacy → Microphone /
  o ponto verde na barra de menus) e que o áudio continua sendo escrito no `.caf`
  (`ls -l ~/Library/Containers/…/Temp/ditado-*.caf` crescendo). Instrumento: `sample` do Ōmu
  mostrando o render block do `inputNode` ativo, ou `log stream --predicate 'process == "Ōmu"'`.
- O que procurei para refutar: (a) procurei `ditado.cancelar()`/`encerrar()` em toda a árvore — só
  a definição existe; (b) procurei `onDisappear`/`task(id:)`/`onChange` em `ArquivoDetalheView`
  que mexessem em `ditado` — o único `onDisappear` é `:513-520` (cita acima); (c) verifiquei se
  `DitadoDeNota` tinha `deinit` ou `@ObservationIgnored` com ciclo — não tem deinit; o retém é só
  o `@State`; (d) verifiquei se `concluir` era chamado automaticamente em algum `task` — o único
  caminho é o botão (`alternarDitado`, `:1386-1401`); (e) verifiquei se `AVAudioEngine` pararia sozinho:
  sem `deinit` dedicado não há garantia no código do projeto (por isso PROVÁVEL e não CONFIRMADO).
- Causa raiz: ciclo de vida do ditado amarrado ao *botão* e não à *tela*; o `onDisappear` encerra
  o player mas esquece o ditado, e o método `cancelar()` ficou órfão.
- Correção sugerida (mínima): adicionar `ditado.cancelar()` ao `onDisappear` de
  `ArquivoDetalheView` (linha 513) — uma linha, risco baixo (cancelar é idempotente: `:571-579`
  só limpa estado). Reforço opcional: `deinit { encerrar() }` em `CapturaDeDitado` e apagar o
  `.caf` órfão na inicialização.

### A2-003: A invariante "Whisper e Qwen nunca residentes juntos" é por *instância*, não global — ditado/diarização concorrentes carregam 2 cópias de 3 GB (e colidem no registro do `CicloDeVidaDeModelos`)
- Severidade: **ALTO**
- Confiança: **PROVÁVEL** (estado concomitante é fato de leitura; o desfecho jetsam é a inferência)
- Local: `Papagaio/ViewModels/Biblioteca.swift:846-861`, `:896`, `:994-1008`, `:987-992`, `:125`;
  `PapagaioCore/Sources/PapagaioCore/Runtime/MotoresLocais.swift:5-27`;
  `PapagaioCore/Sources/WhisperRuntime/ContextoWhisper.swift:82-129` + `WhisperEngine.swift:145-147`;
  `PapagaioCore/Sources/PapagaioCore/Runtime/CicloDeVidaDeModelos.swift:53-55, 68-77`;
  `PapagaioCore/Sources/PapagaioCore/Diarizacao/GerenciadorDeModelosDeDiarizacao.swift:15, 85-87`
- Evidência: a exclusividade vive dentro de uma instância do ator, e a `fila` também:
  ```swift
  // MotoresLocais.swift:5-21
  /// …garantia de que **nunca ficam residentes ao mesmo tempo**…
  public actor MotoresLocais {
      private let fila = FilaEstrita()      // fila POR INSTÂNCIA
  ```
  Mas o app cria uma instância **por operação**, todas apontando para o **mesmo** `ciclo`:
  ```swift
  // Biblioteca.swift:852 (transcreverDitado — ditado de nota)
  let motores = MotoresLocais(pastaDeModelos: pastaDeModelos, ciclo: ciclo)
  // Biblioteca.swift:896 (executarProcessamento — pipeline da fila)
  let motores = MotoresLocais(pastaDeModelos: pastaDeModelos, ciclo: ciclo)
  // Biblioteca.swift:1008 (diarizarTranscricao — ação avulsa)
  let motores = MotoresLocais(pastaDeModelos: pastaDeModelos, ciclo: ciclo)
  ```
  E o registro no ciclo é chaveado por um identificador **estático**:
  ```swift
  // CicloDeVidaDeModelos.swift:53-55
  public func registrar(_ residente: any Residente) {
      residentes[residente.identificador] = residente     // colisão: 1 entrada por nome
  }
  // WhisperEngine.swift:145-147 → "whisper-large-v3"  ·  Gerenciador…:15 → "fluidaudio-community-1"
  ```
  Os guards de `diarizarTranscricao` (`Biblioteca.swift:987-992`) impedem concorrência **com o
  mesmo arquivo** (`arquivoEmProcessamento != arquivo.id`, `!filaDeProcessamento.contains`, …),
  mas nada impede com **outro** arquivo; e `transcreverDitado` (`:846`) não tem guarda nenhuma.
- Cenário de falha: com um áudio longo em transcrição (Whisper#1 residente, 3 GB), a pessoa abre
  outra conversa e dita uma nota → `transcreverDitado` cria `MotoresLocais#2`, que carrega
  **Whisper#2** (outros ~3 GB + uso de GPU/Metal); ou, se o pipeline está na fase de resumo
  (Qwen ~6,2 GB residente), o ditado carrega Whisper → ~9,2 GB de pesos. Dois efeitos:
  (1) é exatamente o cenário que o cabeçalho de `MotoresLocais` (`:5-12`) diz que mata o app por
  jetsam num Mac de 18 GB; (2) o `CicloDeVidaDeModelos` **não consegue aliviar pressão**: os dois
  contextos registram a mesma chave `"whisper-large-v3"`, então `descarregarTudo()` (`:68-77`)
  descarrega só o último registrado, e o `remover(identificador)` da limpeza de um apaga o
  registro do outro — o modelo em uso escapa do monitor.
- Como reproduzir: gravar/importar um áudio >10 min com processamento automático e, enquanto a
  tarja está em "transcrevendo…", abrir outra conversa → Notas → Ditar → concluir. Em
  **Instruments → Allocations/Footprint** observar dois picos de ~3 GB de `ggml`/`whisper` (ou
  duas regiões Metal grandes) e, em `log stream`, adicionar temporariamente um `print` em
  `CicloDeVidaDeModelos.descarregarTudo` listando `residentes.keys` (veria uma chave só).
- O que procurei para refutar: (a) procurei uma fila/global compartilhada entre instâncias de
  `MotoresLocais` — `FilaEstrita` é `private let` por instância (`MotoresLocais.swift:21`), e o
  `static let fila` compartilhado só existe em `DownloadDeModelos.swift:47` e
  `DetectorDeAtividadeDeVoz.swift:59`; (b) verifiquei se `transcreverDitado` entrava na fila de
  processamento da `Biblioteca` — não entra, é chamado direto por `aoDitar`
  (`ContentView.swift:594` → `ArquivoDetalheView.swift:1391`); (c) verifiquei se `diarizarTranscricao`
  era bloqueada durante processamento — os guards de `:987-992` deixam passar com outro arquivo;
  (d) verifiquei se o actor `ContextoWhisper` serializaria tudo — serializa o **uso** (não há
  race/use-after-free), mas não impede duas *instâncias* de existirem; (e) verifiquei
  `ciclo.registrar` — a colisão de chave é direta (`residentes[id] = …`).
- Causa raiz: invariante de memória modelada *dentro* de um objeto que o app instancia várias
  vezes, combinada a um registro global chaveado por identificador estático.
- Correção sugerida: (1) compartilhar **uma** instância de `MotoresLocais` (propriedade da
  `Biblioteca`, como `ciclo`) em vez de criar por operação — muda só 3 pontos
  (`Biblioteca.swift:852/896/1008`) e aproveita a fila existente; alternativa mínima: passar o
  `ciclo` atual e registrar com chave única por instância (`identificador + ObjectIdentifier`).
  Risco baixo; benefício: devolve a invariantede documento e o alcance do monitor de memória.

### A2-004: Variáveis locais mutáveis capturadas por dois callbacks assíncronos do CloudKit (`recordWasChangedBlock` / `fetchRecordZoneChangesResultBlock`)
- Severidade: **MÉDIO**
- Confiança: **PROVÁVEL**
- Local: `Papagaio/CloudKit/SincronizadorDaBibliotecaCloudKit.swift:246-271` (método `registrosDaZona`)
- Evidência:
  ```swift
  // :251-269
  var registros: [CKRecord] = []
  var erroPorRegistro: (any Error)?
  operacao.recordWasChangedBlock = { _, resultado in
      switch resultado {
      case let .success(registro): registros.append(registro)   // muta captura
      case let .failure(erro):     erroPorRegistro = erro       // muta captura
      }
  }
  operacao.fetchRecordZoneChangesResultBlock = { resultado in
      if let erroPorRegistro { … } else { … continuation.resume(returning: registros) }  // lê captura
  }
  banco.add(operacao)
  ```
  São dois closures `escaping` distintos gravando/lendo o mesmo `var` local sem trava, sem
  `actor` e sem `@Sendable`/`Sendable` envolvido; o projeto compila em Swift 6 strict porque o
  SDK do CloudKit ainda importa esses blocos sem `@Sendable` — ou seja, **o compilador não está
  protegendo este ponto** (o build limpo desta auditoria teve 0 warnings de Swift do projeto,
  `audit/00-mapa.md:427-431`).
- Cenário de falha: se o CloudKit entregar um callback de registro numa fila diferente (ou
  sobreposta) à do bloco de resultado, `registros.append` corre com a leitura do `Array` no
  `continuation.resume(returning:)` → data race sobre o buffer do `Array` → leitura corrompida
  (páginas de `CKRecord` inválidas) ou crash de exclusividade (`Simultaneous accesses to …`).
  Segundo risco no mesmo trecho: o `continuation` é retomado **uma única** garantia implícita —
  se a operação nunca chamar `fetchRecordZoneChangesResultBlock` (cancelamento/erro de
  infraestrutura), `baixarComVersoes` (`:382-391`) nunca completa e o `retomarSincronizacaoCloudKit`
  fica preso com `estadoDaSincronizacaoCloudKit = .enviando`.
- Como reproduzir: build com **Thread Sanalyzer** (`xcodebuild test … -sanitize=thread`) e um
  teste/rotina de `baixarComVersoes` contra um Mock `Transporte` não serve — o trecho é o
  transporte real; o caminho é rodar o app com uma equipe ativa e `baixarComVersoes` em zona com
  >200 registros (paginação) sob `log stream`/TSan. Reprodução determinística: extrair o padrão
  (operação com dois callbacks mutando capturas) para um `CKDatabase` de teste com
  `database.add(operation)` e `-sanitize=thread`.
- O que procurei para refutar: (a) procurei serialização — a classe é `actor
  TransporteDeConversasCloudKitReal`, mas os dois closures rodam **fora** do ator (o ator só
  protege o corpo do método, que suspende em `withCheckedThrowingContinuation`); (b) procurei
  `@preconcurrency import CloudKit` ou `@Sendable` — o import é simples (`:1`), logo o SDK não
  está marcado e nenhum dos dois closures é `@Sendable` auditado; (c) procurei lock/queue
  explícita — não há; (d) verifiquei se os callbacks do `CKFetchRecordZoneChangesOperation` têm
  garantia documentada de serialização na mesma fila — **não encontrei essa garantia no SDK**
  (por isso PROVÁVEL); (e) `registros`/`erroPorRegistro` não escapam do método.
- Causa raiz: continuação assíncrona montada sobre estado mutável compartilhado por callbacks da
  API, sem exclusão mútua nem imutabilidade.
- Correção sugerida: trocar os `var` por um `final class Acumulador` com
  `OSAllocatedUnfairLock` (padrão já usado em `SystemAudioTap.swift:431`) **ou** coletar os
  registros via `perRecordBlock` serializado num `actor` local pequeno; e adicionar um
  `operacao.completionBlock` de segurança que retoma a continância com erro se o bloco de
  resultado não veio. Risco baixo, toca um método só.

### A2-005: `MainActor.assumeIsolated` em `presentationAnchor(for:)` — thread de chamada não garantida
- Severidade: **MÉDIO**
- Confiança: **HIPÓTESE**
- Local: `Papagaio/ViewModels/PerfilViewModel.swift:241-248`
- Evidência:
  ```swift
  nonisolated func presentationAnchor(for controller: ASAuthorizationController) -> ASPresentationAnchor {
      // O AuthenticationServices solicita a âncora durante a apresentação
      // do painel. A exigência do protocolo ainda é nonisolated, embora
      // AppKit so permita consultar janelas na main actor.
      MainActor.assumeIsolated {
          NSApplication.shared.keyWindow ?? ASPansionAnchor()   // [sic: ASPresentationAnchor]
      }
  }
  ```
  `MainActor.assumeIsolated` **não verifica nada**: se a thread de quem chama não for a main,
  ele aborta o processo (`fatalError`/precondition). Note a inconsistência interna: os outros
  callbacks do mesmo delegate **não** confiam na thread e envolvem tudo em `Task { @MainActor }`
  (`:213-228`, `:233-236`) — o próprio código demonstra desconfiança da mesma API.
- Cenário de falha: se o AuthenticationServices chamar `presentationAnchor` fora da main thread
  (em algum macOS/build, delegate delivery em fila própria), o app **crasha** na hora do Sign in
  with Apple, sem stack útil. Adicionalmente, mesmo sem trap, `NSApplication.shared.keyWindow`
  fora da main é chamada de AppKit off-thread.
- Como reproduzir: substituir temporariamente o corpo por
  `assert(Thread.isMainThread)` (ou logar `Thread.current`) e clicar "Entrar com Apple" em
  `PapagaioTests`/app; ou rodar o fluxo sob **Main Thread Checker** (Xcode → Edit Scheme →
  Diagnostics → Main Thread Checker ON) e ver se acusa em `presentationAnchor`.
- O que procurei para refutar: (a) verifiquei se a doc/comportamento observável do
  `ASAuthorizationControllerPresentationContextProviding` garante main — **não está escrito no
  protocolo** (é por isso que o método é `nonisolated`); (b) verifiquei se havia um
  `assumeIsolated` equivalente já validado no projeto: os outros dois

### A2-007: `DispatchSemaphore.wait()` bloqueando a main thread no encerramento do app
- Severidade: **BAIXO**
- Confiança: **PROVÁVEL** (o bloqueio é determinístico no código; a percepção depende do custo de `descarregar`)
- Local: `PapagaioCore/Sources/PapagaioCore/Runtime/CicloDeVidaDeModelos.swift:91-115`
- Evidência:
  ```swift
  observadorDeSaida = NotificationCenter.default.addObserver(
      forName: Notification.Name("NSApplicationWillTerminateNotification"),
      object: nil, queue: .main) { [weak self] _ in
          guard let self else { return }
          let espera = DispatchSemaphore(value: 0)
          Task { await self.descarregarTudo(); espera.signal() }
          _ = espera.wait(timeout: .now() + 2)   // ← main thread bloqueada até 2 s
      }
  ```
- Cenário de falha: ao fechar o app com modelo residente, a main fica travada até 2 s (o
  `descarregarTudo` percorre `residente.descarregar()` de um `whisper` 3 GB e de um `llama` 6,2 GB
  — `:68-77`). Se o ator estiver ocupado (ex.: um descarga por pressão de memória em voo) a espera
  estoura no teto e o processo sai com unload parcial — comportamento que o comentário `:102-107`
  declara aceitável, mas que é exatamente o risco de `GGML_ASSERT` descrito em `:81-87` se o
  ponto de saída for atingido no meio da liberação. Bônus: `observadorDeSaida` nunca é removido
  (irrelevante só porque é notificação de saída).
- Como reproduzir: com um processamento residente, fechar o app medindo o tempo entre ⌘Q e o
  processo sumir (`log stream`/`ps` em loop), ou Instruments Time Profiler no
  `-[NSApplication terminate]` mostrando `semaphore_wait_trap` na main.
- O que procurei para refutar: (a) o observer usa `queue: .main` **e** o handler é síncrono — o
  bloqueio da main é inevitável neste desenho; (b) o teto de 2 s existe e limita o dano (daí
  BAIXO); (c) verifiquei deadlock real: o `Task` roda no executor global e `descarregar` dos
  `Residente` (`ContextoWhisper.descarregar` `:126-129`, `ContextoLlama.descarregar` `:101-106`,
  `GerenciadorDeModelosDeDiarizacao.descarregar` `:70-72`) não dependem da main → **não há
  deadlock**, só bloqueio limitado; (d) `atexit`/outros caminhos de saída não existem no código.
- Causa raiz: necessidade síncrona ("depois deste retorno o processo sai") resolvida com espera
  bloqueante na main.
- Correção sugerida: em vez de semáforo, chamar a liberação dos ponteiros C **sincronamente**
  (expor um `não-async descarregarSincrono()` nos `Residente` que só `whisper_free`/`llama_free`,
  já que essas chamadas são C puro) a partir do handler; ou manter o semáforo mas com teto de
  ~300 ms. Risco médio-baixo (toca caminho de saída — testar quit com e sem modelo residente).

### A2-008: Caches estáticos de UI sem limite (`urlsResolvidas`, `CorDominanteDeImagem.memoria`)
- Severidade: **BAIXO**
- Confiança: **PROVÁVEL**
- Local: `Papagaio/Persistencia/FotosDePessoas.swift:35`, `Papagaio/Persistencia/AparenciaDoCartao.swift:81`, `Papagaio/Persistencia/AparenciaDasPastas.swift:234`, `Papagaio/Persistencia/CorDominanteDeImagem.swift:17`
- Evidência:
  ```swift
  // FotosDePessoas.swift:35 · AparenciaDoCartao.swift:81 · AparenciaDasPastas.swift:234
  @MainActor private static var urlsResolvidas: [String: URL?] = [:]
  // CorDominanteDeImagem.swift:17
  @MainActor private static var memoria: [String: Color] = [:]
  ```
  Dicionários `static` crescem por inserção (`FotosDePessoas.swift:47-67`,
  `CorDominanteDeImagem.swift:26-29`) e só são apagados por `remover`/`renomear`/`esquecer`/
  `esquecerTudo` (`FotosDePessoas.swift:85-91, 102-119, 158-166`); não há LRU, teto nem expiração.
- Cenário de falha: biblioteca com centenas de conversas/pastas/pessoas: cada chave retém uma
  `URL?` (~100 B) + uma `Color`; entradas de conversas **apagadas definitivamente** não passam por
  `esquecer` (que é acionado por fotos/pastas, não por `apagarDefinitivamente`) e ficam para sempre
  na vida do processo. Crescimento lento e sem fim de sessão (é `static`, sobrevive à troca de tela).
- Como reproduzir: rodar o app, percorrer biblioteca grande, e medir com Instruments **Allocations**
  (filter `FotosDePessoas` / `CorDominanteDeImagem`) antes/depois de apagar dezenas de conversas;
  ou `po`/LLDB `x/50wa` no dicionário. Vale notar que as *imagens* estão protegidas: usam
  `NSCache` (`FotosDePessoas.swift:30`, `AparenciaDoCartao.swift:71`, `AparenciaDasPastas.swift:230`),
  que tem limite automático de memória.
- O que procurei para refutar: (a) isolamento — todos são `@MainActor`, **não** há race; (b)
  imagens: `NSCache` (auto-evicção) — ok; (c) tamanho por entrada: `URL`/`Color`, centenas de
  bytes — por isso BAIXO; (d) verifiquei limpeza em exclusão de conta: `removerTodas`/`esquecerTudo`
  existem e são chamados na cascata de exclusão (`ContentView.swift:913-918` → `FotosDePessoas.removerTodas`),
  então o vazamento é só no caminho de exclusão individual de conversa.
- Causa raiz: memoização pensada para a vida da sessão, sem política de substituição.
- Correção sugerida: limitar com `NSCache` também para os `URL`/`Color`
  (`NSCache<NSString, NSURL>`) ou chamar `esquecer`/`remover` em `Biblioteca.apagarDefinitivamente`
  (`:469-505`) ao lado de `LimpezaDeArquivo.executar` (`:501`). Risco baixo.
